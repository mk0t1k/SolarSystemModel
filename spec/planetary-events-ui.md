# Feature Specification: Поиск и визуализация планетарных событий

**Feature File**: `spec/planetary-events-ui.md`

**Status**: Draft

**Input**: Основной пользовательский сценарий «Поиск и визуализация планетарных событий»: выбор типа астрономического явления, выбор планет-участников, указание горизонта прогноза, валидация, блокировка повторной отправки, состояния загрузки/успеха/пустого ответа/ошибки расчёта и интеграция с перемоткой времени симуляции на 3D-орбите.

---

## 1. User Scenarios & Testing *(mandatory)*

### User Story 1 - Настройка параметров и поиск планетарного события (Priority: P1)

Как исследователь космоса или пользователь симулятора Солнечной системы, я хочу задавать тип астрономического явления (Соединение, Противостояние, Парад планет), выбирать минимум 2 планеты-участника и указывать горизонт прогноза в днях, чтобы находить ближайшие редкие астрономические конфигурации и визуализировать их на орбите.

- **Acceptance Scenario 1.1 (Значения по умолчанию и структура формы)**:
  Given панель поиска планетарных событий открыта,
  When пользователь просматривает форму,
  Then переключатель «Тип явления» (`SelectButton`) по умолчанию имеет значение «Соединение» (варианты: «Соединение», «Противостояние», «Парад планет»),
  And список участников отображает доступные планеты с помощью компонентов PrimeVue (например, `ToggleButton` или чекбоксы `Checkbox`),
  And поле «Горизонт прогноза (земных дней)» представлено компонентом `InputNumber` с допустимым диапазоном от 1 до 3650 дней,
  And у всех полей формы присутствуют связанные `<label>` (`for` / `id`).

- **Acceptance Scenario 1.2 (Успешный поиск и отображение результата)**:
  Given выбраны корректные параметры:
    - Тип явления: «Соединение» (или «Противостояние» / «Парад планет»)
    - Участники: выбрано 2 или более планеты (например, Земля и Марс)
    - Горизонт прогноза: числовое значение в диапазоне от 1 до 3650 дней,
  When пользователь нажимает кнопку «Найти событие» (`Button`) или нажимает клавишу `Enter`,
  Then запускается асинхронный расчёт события,
  And на время ожидания кнопка переходит в состояние `loading` / `disabled`,
  And под формой отображаются скелетоны PrimeVue `Skeleton`,
  And при успешном нахождении события под формой отображается карточка PrimeVue `Card` со сведениями:
    - дата события,
    - участвующие планеты,
    - угловое расстояние между ними,
  And в карточке присутствует кнопка PrimeVue `Button` «Показать на орбите».

- **Acceptance Scenario 1.3 (Перемотка времени на дату события)**:
  Given в результате успешного поиска отображается карточка с найденным событием,
  When пользователь нажимает кнопку «Показать на орбите»,
  Then время симуляции перематывается на точную дату и время найденного события,
  And позиции планет на 3D-сцене `SolarScene` обновляются в соответствии с вычисленной конфигурацией.

### User Story 2 - Валидация полей формы (Priority: P1)

Как пользователь, я хочу получать наглядные и понятные сообщения об ошибках валидации при некорректном заполнении формы, чтобы быстро исправить введённые параметры.

- **Acceptance Scenario 2.1 (Валидация количества выбранных планет)**:
  Given в списке участников выбрано меньше 2 планет (0 или 1 планета),
  When пользователь пытается отправить форму (или кнопка отправки анализирует состояние формы),
  Then кнопка отправки заблокирована (`disabled`) ИЛИ при попытке отправки выводится ошибка валидации:
    `«Выберите минимум 2 планеты для расчёта»`,
  And асинхронный расчёт не инициируется.

- **Acceptance Scenario 2.2 (Валидация горизонта прогноза)**:
  Given поле «Горизонт прогноза (земных дней)» оставлено пустым, либо введено значение меньше 1, либо больше 3650 дней,
  When выполняется валидация формы при отправке,
  Then выводится ошибка валидации:
    `«Укажите горизонт прогноза от 1 до 3650 дней»`,
  And асинхронный расчёт не запускается.

### User Story 3 - Блокировка повторной отправки и обработка асинхронных состояний (Priority: P1)

Как пользователь, я хочу быть защищённым от повторных кликов во время долгих расчётов и видеть однозначную обратную связь для каждого исхода (загрузка, пустой результат, ошибка).

- **Acceptance Scenario 3.1 (Предотвращение дублирующих расчётов)**:
  Given форма заполнена валидно и запущен асинхронный расчёт (pending),
  When пользователь повторно кликает по кнопке «Найти событие» или нажимает клавишу `Enter`,
  Then кнопка остаётся в состоянии `loading` / `disabled`,
  And повторный параллельный вызов расчёта не запускается.

- **Acceptance Scenario 3.2 (Состояние загрузки)**:
  Given выполняется асинхронный расчёт события,
  When результат ещё не получен,
  Then область результатов под формой отображает плейсхолдеры загрузки PrimeVue `Skeleton`.

- **Acceptance Scenario 3.3 (Пустой результат поиска)**:
  Given расчёт завершился успешно, но за указанный горизонт дней событий выбранного типа не найдено,
  When система возвращает пустой список результатов,
  Then под формой выводится информационное сообщение:
    `«За указанный период таких явлений не найдено. Попробуйте увеличить горизонт прогноза»`.

- **Acceptance Scenario 3.4 (Ошибка расчёта или сбой API)**:
  Given асинхронный расчёт завершился сбоем (ошибка вычислений, сетевой сбой или ошибка API),
  When промис отклоняется,
  Then все ранее выбранные пользователем параметры (тип явления, выбранные планеты, горизонт прогноза) сохраняются в форме без изменений,
  And сверху или под формой отображается баннер PrimeVue `Message` (`severity="error"`) с текстом ошибки и кнопкой «Повторить попытку»,
  And кнопка отправки возвращается в доступное состояние для повторного запуска.

### User Story 4 - Доступность и адаптивность интерфейса (Priority: P2)

Как пользователь с клавиатурным управлением или пользователь мобильного устройства, я хочу удобно взаимодействовать с формой на экранах шириной от 375px и управлять всеми элементами без мыши.

- **Acceptance Scenario 4.1 (Связанные лейблы и ARIA)**:
  Given форма поиска планетарных событий отображается в интерфейсе,
  When разметку анализирует браузер или скринридер,
  Then у всех полей ввода присутствуют связанные теги `<label>` с корректными атрибутами `for` / `id`,
  And группы переключателей снабжены доступными именами (`aria-label` / `aria-labelledby`).

- **Acceptance Scenario 4.2 (Управление с клавиатуры и фокус)**:
  Given пользователь взаимодействует с панелью только с клавиатуры,
  When пользователь нажимает `Tab` / `Shift+Tab`,
  Then фокус последовательно перемещается между интерактивными элементами (SelectButton, кнопки/чекбоксы планет, InputNumber, кнопки отправки и повтора),
  And каждый интерактивный элемент имеет отчётливо видимый индикатор `:focus-visible`,
  And выбор планет и переключение типа осуществляются клавишами `Space` / стрелками / `Enter`,
  And отправка формы инициируется нажатием `Enter` в числовом поле ввода,
  And нажатие `Escape` закрывает/сворачивает панель (если она представлена в виде модального окна или шторки).

- **Acceptance Scenario 4.3 (Адаптивность для узких экранов)**:
  Given ширина области просмотра составляет 375px (мобильный экран),
  When отображается панель поиска и карточка результата,
  Then элементы формы, кнопки выбора планет и карточка события корректно переносятся, не вызывают горизонтальной прокрутки страницы и сохраняют минимальную область клика (touch target).

## 2. Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Поле «Тип явления» MUST быть реализовано с помощью компонента PrimeVue `SelectButton` с опциями: «Соединение», «Противостояние», «Парад планет». Значение по умолчанию MUST быть «Соединение».
- **FR-002**: Выбор планет-участников MUST производиться с использованием компонентов PrimeVue (`ToggleButton` или `Checkbox`).
- **FR-003**: Система MUST требовать выбор как минимум 2 планет-участников. Если выбрано менее 2 планет, кнопка отправки MUST быть заблокирована (`disabled`) ИЛИ при попытке отправки MUST отображаться сообщение валидации: `«Выберите минимум 2 планеты для расчёта»`.
- **FR-004**: Поле «Горизонт прогноза (земных дней)» MUST быть обязательным полем на базе PrimeVue `InputNumber` с допустимым диапазоном значений от 1 до 3650 дней.
- **FR-005**: При пустом значении или выходе за диапазон `[1, 3650]` система MUST отображать ошибку валидации: `«Укажите горизонт прогноза от 1 до 3650 дней»` и блокировать запуск расчёта.
- **FR-006**: При клике на кнопку «Найти событие» или нажатии клавиши `Enter` система MUST запускать асинхронный расчёт. На время расчёта кнопка отправки MUST переходить в состояние `loading` / `disabled`, а повторные клики и нажатия `Enter` MUST блокироваться.
- **FR-007**: На время ожидания завершения расчёта область результатов под формой MUST отображать плейсхолдеры PrimeVue `Skeleton`.
- **FR-008**: При успешном обнаружении события система MUST отображать карточку PrimeVue `Card`, содержащую:
  - дату события,
  - список участвующих планет,
  - угловое расстояние между телами,
  - кнопку PrimeVue `Button` «Показать на орбите».
- **FR-009**: При клике на кнопку «Показать на орбите» время симуляции MUST перематываться на дату события с немедленным обновлением орбитальных позиций тел на 3D-сцене `SolarScene`.
- **FR-010**: Если за указанный горизонт дней событий не найдено, система MUST отображать понятное сообщение: `«За указанный период таких явлений не найдено. Попробуйте увеличить горизонт прогноза»`.
- **FR-011**: При ошибке расчёта или сбое API:
  - все выбранные пользователем параметры (тип явления, планеты, горизонт прогноза) MUST сохраняться без изменений,
  - сверху или под формой MUST отображаться баннер PrimeVue `Message` (`severity="error"`) с описанием ошибки и кнопкой «Повторить попытку».
- **FR-012**: У всех полей формы MUST быть связанные теги `<label>` (`for` / `id`). Вся панель MUST полноценно управляться с клавиатуры (`Tab`, `Space`, `Enter`, `Escape`) с заметным индикатором `:focus-visible`.
- **FR-013**: Интерфейс панели MUST оставаться удобным и полностью функциональным на экранах шириной от 375px без появления паразитной горизонтальной прокрутки.
- **FR-014**: Запрещено использование нативных тегов `<button>`, `<input>`, `<select>`. Весь UI MUST строиться исключительно на компонентах PrimeVue (тема Aura в тёмном режиме): `SelectButton`, `ToggleButton` / `Checkbox`, `InputNumber`, `Button`, `Card`, `Skeleton`, `Message`.

### Data Models & Contracts

```typescript
export type PlanetaryEventType = 'conjunction' | 'opposition' | 'alignment';

export interface PlanetaryEventFilter {
  eventType: PlanetaryEventType;
  planetIds: string[];
  forecastDays: number;
}

export interface PlanetaryEventResult {
  id: string;
  eventType: PlanetaryEventType;
  date: string;            // ISO 8601 строка даты/времени события
  timestamp: number;       // Симуляционное время в миллисекундах
  planetIds: string[];     // Участники события
  angularSeparationDeg: number; // Угловое расстояние (градусы)
  description?: string;
}

export interface PlanetaryEventCalculationResponse {
  success: boolean;
  event?: PlanetaryEventResult | null;
  error?: string;
}
```

## 3. Success Criteria *(mandatory)*

- **SC-001**: При любых некорректных параметрах (менее 2 планет, горизонт вне 1..3650 или пуст) отображаются регламентированные сообщения об ошибках, и расчёт не запускается.
- **SC-002**: Во время расчёта полностью исключены параллельные дублирующие вызовы от повторных кликов или нажатий `Enter`.
- **SC-003**: При возникновении сетевой или алгоритмической ошибки пользовательские параметры не сбрасываются, а кнопка «Повторить попытку» позволяет сразу перезапустить расчёт.
- **SC-004**: Нажатие кнопки «Показать на орбите» мгновенно синхронизирует время симуляции и трёхмерное положение планет в `SolarScene`.
- **SC-005**: 100% интерактивных элементов доступны для управления с клавиатуры с видимым индикатором `:focus-visible`, а разметка корректно отображается на экране шириной 375px.
